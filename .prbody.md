### What this PR does

Before this PR:

When MCP tools return images (base64-encoded), the same data is stored redundantly in both the ToolBlock (`rawMcpToolResponse.response`) and the ImageBlock (`generateImageResponse`). Over multiple tool calls, JS heap balloons to **1 GB+** (measured: 924 MB of strings, 84% of heap). Meanwhile, `store.subscribe` serializes the **entire** Redux state (including these large slices) via IPC to the main process every 100ms. Since serialization takes 200-500ms — longer than the throttle interval — the main thread is **continuously blocked**, causing persistent UI freezes.

After this PR:

1. **Strip redundant base64 from ToolBlock**: Images are extracted before `MCP_TOOL_COMPLETE` is emitted, and the heavy base64 payload in the tool response is replaced with a lightweight placeholder. The ImageBlock continues to hold the actual image data. The ToolBlock UI (`extractPreviewContent`) only reads `content.mimeType`, never `content.data`, so display is unaffected.

2. **Exclude large slices from IPC sync**: `messages` and `messageBlocks` are excluded from the IPC payload sent to the main process. These slices are already blacklisted from Redux Persist and are never read by the main process (`ReduxService.selectSync` / `stateCache` has no consumers accessing message or block data — verified by codebase search).

**Measured results** (same workload, ~24 generated images):

| Metric | Before | After | Improvement |
|--------|--------|-------|-------------|
| JS Heap | 1,077 MB | 341 MB | **-68%** |
| IPC serialization per cycle | 200-500ms (continuous freeze) | <1ms | **Eliminated** |
| User experience | Persistent UI freeze | Smooth | |

Fixes #12214

### Why we need it and why it was done in this way

The root cause is two independent issues that compound:

1. **Data duplication**: `handleToolResult` in `handleToolCallChunk.ts` emits `MCP_TOOL_COMPLETE` (with full base64) then `IMAGE_COMPLETE` (with the same base64 extracted as data URLs). Both get stored in Redux as separate blocks. Each image costs ~2MB x 2 copies = ~4MB in Redux state.

2. **IPC over-serialization**: `store.subscribe` sends the full `store.getState()` to the main process every 100ms. With `messageBlocks` containing hundreds of MB of base64, the serialization alone blocks the main thread longer than the throttle interval, causing continuous freezes.

The following tradeoffs were made:

- ToolBlock's copy button (`JSON.stringify(result)`) will now show the placeholder `[image data moved to ImageBlock]` instead of raw base64. This is arguably more useful than a multi-MB base64 string in the clipboard.

The following alternatives were considered:

- **Save images to files (file:// references)**: Would eliminate base64 from ImageBlock too, reducing heap to ~50MB. However, this changes the ImageBlock data model and conflicts with the v2 refactor policy. Recommended as a follow-up.
- **Virtual scrolling for message list**: Would help with DOM node count in very long conversations. Orthogonal to this fix and also a larger architectural change.

### Breaking changes

None. Both changes are purely internal optimizations:
- No Redux state shape changes
- No IndexedDB schema changes
- No UI behavior changes
- No API changes
